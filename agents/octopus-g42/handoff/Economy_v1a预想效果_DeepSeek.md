# Economy v1a 预想效果（动手前的预测，对话37）

写成文件是为了留档：事后可以拿实机数据核对这份预测，而不是"做完了再解释它有什么用"。
数据来源：`battle-1790430446053-d2ee6fee.jsonl`（巨岛 981s，v0.1 生效局）、
`battle-1790434276497-7c4a6933.jsonl`（巨岛 580s，1x→5x 渐进，VICTORY）。

## 一、v1a 改变的是什么（一句话）

现在：**生产优先，花不完的钱才拿去投资**——所以额外矿只在军队触顶、现金堆起来之后才出现。
v1a 之后：**可以先立一个投资意图，把这笔钱从生产通道手里扣住**，于是额外矿能在军队还没触顶时就开出来。

机制上只加一个东西：`investment_intent(NEW_MINE) + investment_reserve`（外加最小的"军队健康"闸门，
避免在挨打时抽走产能）。

## 二、为什么"更早"才是重点——这条数据修正了我原本的直觉

我原本以为 v1a 的收益是"能开更多矿"。用报告实测估算**收入率**（余额变化 + 造兵花费，按 120 秒窗口）：

| 窗口 | 矿数（中位） | 估算收入 |
| --- | --- | --- |
| 120–240s | 2 | 40.2/s |
| 240–360s | 3 | **56.8/s** |
| 360–480s | 3 | **62.7/s** |
| 480–600s | 3 | 50.0/s |
| 600–720s | 3 | 58.7/s |
| 720–840s | 3 | 48.1/s |
| 840–960s | **5** | **58.8/s** |

**矿从 3 座加到 5 座，收入率没有可见变化（都在 50–63/s 之间）。** 这不是"矿没用"，
而是**这局多出来的矿来得太晚**：轨迹是 3 座(240s) → **4 座(600s)** → 4 座(840s) → **5 座(900s)**，
而比赛 981 秒结束——最后那两座只活了 80～140 秒，根本来不及回本（每座 700）。

也就是说：v0.1 现在做的是"**在最没用的时刻**开矿"。v1a 的价值不在于数量，而在于**把同一座矿提前 200～500 秒**。

## 三、代价（同样用实测数据算）

军队建设期（240–480s）收入约 **57–63/s**。

- 扣住 700 ⇒ 相当于**约 12 秒的全部收入**；
- 按首选单位 heavyTank 800 计 ⇒ **约 0.9 辆重坦**；按 c_tank 350 计 ⇒ **约 2 辆小坦**。

即"用不到一辆重坦的产能，换一座能活几百秒的矿"。**只要发生在比赛前半段，这笔交易明显划算；
发生在最后 100 秒就是纯亏**——而这正是 v0.1 现在做的事。

## 四、具体预测（可被实机证伪）

| 局面 | v0.1 实测 | v1a 预测 |
| --- | --- | --- |
| 巨岛 981s（480s 后开始堆钱） | 额外矿在 ~600s、~840s、~900s，全部发生在 army ≥34 时 | **第一座额外矿提到 ~300–400s**，即在 army 触顶前；总数 3～6 座 |
| 1x→5x 短局（580s VICTORY，army 峰值 37） | **0 座**，24 次 `NO_SURPLUS` | **≥1 座**——钱以收入形式存在，只是从来没攒成一堆 |
| 低收入局（湖陆 981s，余额中位 452） | 0 座 | 0～1 座，且应当**晚**（收入低时扣 700 的代价太大，闸门应当拒绝） |

**可证伪的核心预测**：出现一条可解释链
`investment_intent(NEW_MINE)` → `intentional_banking`（预留期间生产被拒并写明原因）→
**在 `army < mobileUnitHardCap` 时完成新矿** → 之后生产恢复。
如果实机里新矿**仍然全部**出现在 army ≥ cap 时，说明 v1a 没起作用，chain 没打通。

## 五、明确不会改变的

- **收入率本身**（不新增任何经济机制，只改投资时机）；
- 兵种结构、战斗策略、目标选择；
- **不会让本来要输的局赢**：我们目前**没有任何证据**表明矿数与胜负相关——最近这局 580s VICTORY 只多开了 2 座矿。
  v1a 的真正意义是补上后续经济工作（升矿/升厂/新厂/存钱）都需要的那个抽象层，
  而不是"这一步就能变强"。

## 六、我要防的失败模式（这个才是真风险）

1. **预留卡死（最危险）**：立了意图、把钱扣住，但建造者过不去（点位不安全/被占/太远），
   于是钱被永久冻结、生产被永久节流。→ 必须有**预留超时**：N 游戏秒内花不掉就释放、撤销意图、重新评估。
2. **在错误时刻抽产能**：军队正在被压、刚连续掉兵时扣 700，可能丢单位或丢建筑。
   → "军队健康"闸门 + 遇袭即释放。
3. **与既有预留打架**：现在已经有 `builderReserve`、`PRIMARY_TECH_BANKING`、`SECONDARY_INVESTMENT`
   三类预留。再加一类若不做优先级，可能出现"谁都以为别人会出钱"或"多头同时扣钱把生产锁死"。
   → 必须明确定义优先级与合计上限。
4. **计量方法本身不可靠**：第二节的收入估算是"余额变化 + 造兵花费"，漏了建筑花费与升级花费，
   噪声约 ±20%——**这一点足以淹没一座矿的真实贡献**。所以 v1a 的验收里应当**顺带测量单矿收入增量**，
   而不是假定社区资料的"58 秒回本"（那张表在核验清单里明确标着"待实测"）。

## 七、我建议的验收（三步，一步一局）

1. 一局巨岛 1x：看 chain 是否出现，第一座额外矿是否早于 army 触顶；
2. 一局 1x→5x 渐进：看 v1a 在倍速下语义是否一致（预留超时按 game time 计，不受倍速影响）；
3. 对照：同一条件跑 v0.1 与 v1a 各一局，比较"额外矿出现时刻"与"比赛结束时余额"。

如果第 1 步就看不到 chain（额外矿仍在触顶后），**先不继续 v1b**，回头查闸门是不是太严。
