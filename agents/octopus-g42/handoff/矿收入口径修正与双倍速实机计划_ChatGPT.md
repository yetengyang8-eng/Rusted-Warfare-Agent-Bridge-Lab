# ChatGPT → DeepSeek：矿收入口径修正 + 用户双倍速实机计划

用户刚补充一个关键口径：机制库里的“58秒回本”按玩家语境应理解为**现实可掐表的普通秒**；在1x下它与普通 game-second 数值基本一致，而不是40-tick 的0.66s经济单位。
同时，T1矿显示“+8”，结合“1经济单位≈0.66现实秒”，有：8 / 0.66 ≈ 12.1 / 普通秒；700 / 12.1 ≈ 58秒。三条信息互相吻合。

因此建议不要把当前长局回归得到的 `10.1 / game-s` 直接提升为机制常数，也不要用它覆盖 12.1。当前应分层记录：
- **机制先验**：T1矿 ≈ 12.1 / 普通 game-second（+8/0.66 与 700/58 互相印证）；
- **实战账本回归值**：≈10.1 / game-second（复杂长局、60s窗口、当前脚本方法得到）。

当前 10.1 的方法存在已知偏差来源：
1. 名义60s窗口实际用窗口内首末 observation 的余额差，但固定除60；5x下真实首末跨度通常不足60 game-s；
2. 矿在窗口中途完成时用矿数中位数代表整窗，会把“半窗享受新增矿”的收入当成“整窗高矿数”，压低斜率；
3. 矿数与比赛时间单调相关，任何时变漏账/退款/其他收入结构都可能被斜率吸收；
4. `ledgerSum == summary.spendTotal` 证明账本内部闭合，不等于证明游戏内所有实际资金流都已捕获。

建议：在用户新实机回来前，不要把10.1硬编码为v1b唯一依据。## 建议的只读重算
用现有两局先做一次更干净的分析即可：
- 只保留矿数在整个窗口内都不变的区间；
- 分母改成 `lastObservationGameTime - firstObservationGameTime` 的真实跨度，不固定写60；
- 排除矿刚完成、升级切换、退款/异常边界附近的过渡窗口；
- 再做回归，看斜率是否向 12 靠近。
如果仍不一致，保留“机制先验12.1 / 实战估计X”的双值，不要为统一数字拖住主线。

## 用户即将提供的新样本
用户现在会亲自再打两局：
1. 一局 **5倍速**；
2. 一局 **1倍速**。

这两局回来后建议一起看，而不是提前调参。优先比较：
- 同样经济行为在1x/5x下是否语义一致；
- investment intent / reserve / release 是否正常；
- builder idle 的主要归因是否仍是 post-release cooldown、NO_SURPLUS、NO_INVESTMENT_INTENT 等；
- 按真实 game-time 计算的收入估计是否受倍速影响；
- 额外矿完成时 army 是否仍能低于 hardCap。

本轮先不要因为10.1 vs 12.1而修改策略常数；等这两局样本回来再一起裁决。
