# Codex：vNext 能力扩张与路线决策合同（2026-09-27）

当前基线：A/B campaign v0 已被 DeepSeek 独立 ACCEPT（E2+E3）；WinError 5 已定位为 Windows 下 campaign.json 被并发只读句柄占用导致 os.replace 失败，并已做有界重试加固；Java 策略语义未改。

本轮不再围绕 cap32/cap40 做“为了测试而测试”。A/B campaign 以后作为开发后的验证仪器：先做真实能力，再并行对抗、统计、看回放、修正。

用户刚完成一项关键实测：桌面版设置中“保存多人录像”开启后，单人遭遇战仍不产出 .replay；多人模式会产出 .replay；同为单人模式的沙盒中存在“启动录像”功能，用户确认它记录的是原生回放而非视频。由此有两条潜在路线：
1. 迁移/复用沙盒的“启动录像”通道，让遭遇战/headless 在开局自动进入原生 replay recorder；
2. 将实验环境逐步迁移到多人 Match，以同时解锁 Agent vs 原版 AI、Agent vs Agent、Agent vs 真人，以及原生 replay。

你可以自行判断先后顺序、施工深度和子智能体拆分，不必机械追求最小实现，也不要求本轮把以下所有能力全部做完。目标是选出当前价值/风险比最高、能形成真实能力跃迁的一组工作并尽量推进。

## 预期能力方向 A：Match / Replay / Self-play 基础

长期目标是形成统一比赛入口：创建 Match → 分配 P1/P2 槽位 → P1/P2 可分别绑定 Agent、原版 AI 或真人 → 命令严格归属各自 team/player → 只读取各自合法信息 → 原生结算 → 自动生成 replay。

优先调查并尽量施工：现有 HeadlessRunner/bridge 与多人 Match 创建、玩家槽位、team/playerId、命令归属、胜负结算之间还缺什么；同局双 Agent 是否能在不重开 P0/Diagnostic Lab 的前提下安全接入。

同时请调查沙盒“启动录像”对应的真实引擎入口。如果只是一个可安全调用的 recorder 开关/方法，可考虑先让现有遭遇战/headless 自动录制；若需要侵入高风险引擎状态，则只给出证据和风险图，不要硬做。
## 预期能力方向 B：经济 vNext

用户希望经济进入“先形成稳定底盘，再强化经济，再扩产能/科技”的阶段，而不是矿数和厂数线性绑定。直观目标类似：先做到约 3矿2厂，然后优先提高经济，再决定加产能或科技；不能出现“3矿就3厂”导致连基础坦克都养不起的结构。

请延续现有 Budget / Investment Manager、动态工厂与实测收入模型，不推翻已验证机制。重点考虑让投资候选真正竞争：NEW_MINE、MINE_UPGRADE、NEW_FACTORY、FACTORY_UPGRADE、NEW_BUILDER、SAVE。

原则：第三厂及以后必须由长期可持续现金流、实际工厂利用率、承诺支出与恢复储备共同证明，而不是由矿数直接触发；经济增强应能反过来支撑更高产能或科技，而不是先堆空产能。

如果你判断“3矿2厂”不应写死，请保留它作为用户意图/阶段示例，设计成状态或能力门槛，而不是硬编码常数。

## 预期能力方向 C：World Model / 侦察 v0

当前 Agent 的“看到即打、进雾易失忆”应逐步升级为最小战争记忆。候选能力包括：敌方 unitId 持久跟踪；最后可见位置与时间；VISIBLE / LOST_CONTACT / CONFIRMED_DEAD；静态地图矿点等公共知识与动态敌情分离。

游戏内侦察可考虑：残血单位转为 EXPENDABLE_SCOUT；必要时专门派侦察者；未来再扩侦察机。目标不是一次做完整高手级推断，而是先让 Agent 真正“记住一场战争”。

战斗组织后续候选：MAIN_FORCE / SCOUT / EXPENDABLE_SCOUT / BUILDER 等角色；多任务组；残血撤退/侦察；目标价值；地面单位避免追逐不可兼容目标；优势时优先拆基地/工厂/关键防御。

本轮不要求同时做复杂兵种克制。更理想的顺序是：先能看到和记住敌情 → 能组织角色/任务组 → 再让兵种生产和反制利用这些信息。
## 执行原则

你可以自主决定：本轮先实现哪一组、哪些只做只读侦察、是否开子智能体、需要多少个子智能体，以及什么时候停止扩并发。不要为了“覆盖面”机械开很多 agent；若新增子智能体的边际收益低，请主动收束。

同一共享工作区同一时刻尽量只有一个代码 owner；其它子智能体优先只读分析并回传结论。最终交接请明确说明用了多少子智能体、各自任务、哪些结论已进入实现、哪些只是建议。

优先复用当前已 ACCEPT 的 campaign / parallel / crash-recovery / profile / aggregate 基础设施。不要无故重写已经验收的层。

若需要做策略改动，请保持可回退、可对比，并尽快用现有 campaign 做真实回归/对抗验证。A/B 只用于验证有意义的新能力，不需要现在为 cap32/cap40 继续扩大样本。

## 安全与边界

- 不允许通过读取敌方隐藏状态来获得超出合法视野的信息；多人/self-play 必须严格按各自玩家视角。
- 不允许为了 replay/self-play 直接写未知的运行时引擎状态；若触及 Diagnostic Lab/P0 相邻反射或高风险内部对象，先只读取证并停下来交接。
- 不要扩到无必要的 4+ 实例并发；当前重点是“同一局的两个玩家”而不是“更多独立游戏进程”。
- 不做为了好看而单独扩建 HTML viewer。原生 replay 若能打通优先；HTML viewer 保留做 Agent 视角诊断。
- 不要根据极小样本直接自动调参或宣布某策略更优。

## 本轮期望交付

请先快速审计现状并自行选定推进路线，然后尽可能交付真实可运行能力，而不只是路线文档。若某方向因风险/接口缺失不宜施工，请给出明确证据、阻断点和下一步最短路径。

理想的本轮结束状态不是“所有方向都碰一点”，而是至少有一个明显能力跃迁，例如：同局双 Agent/多人 Match 原型成立；或现有 headless 能自动产出原生 replay；或经济 vNext/World Model v0 中一项形成可实机验证闭环。

完成后请写正式 HANDOFF，包含：实现内容、未实现内容、测试/实机证据、当前 SHA/身份边界、失败与风险、建议下一步，以及本轮子智能体使用情况。
