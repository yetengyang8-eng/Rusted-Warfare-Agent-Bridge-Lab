# 0.01-alpha2：实测反馈与修复

## 结论

第二、三次停止的直接原因是 Agent 的返程边界校验错误，不是单位不接受移动命令，也不是因为中途受伤。第一、二次不应发生的长距离移动同样来自错误的地图尺寸。

| 报告 | 起点 | alpha1 目标 | 记录结果 |
|---|---|---|---|
| roundtrip-1789905400863-80801859.jsonl | (990,1730) | (180,180) | 45 秒到达超时；最后坐标 (530.037,310.004)，30/170 HP，dead=false |
| roundtrip-1789905557413-28317e21.jsonl | (988.95,1862.397) | (180,180) | 约 13.9 秒识别去程到达；返程 HTTP 400 target is outside map bounds |
| roundtrip-1789905658080-044b683e.jsonl | (940,1780) | (180,180) | 约 30.3 秒识别去程到达；返程同样 HTTP 400，全程采样 1000/1000 HP |

用户观察第一次建造者被敌军打死；日志只采样到超时前残血存活，不能从该日志确认死亡时刻。不能将超时写成程序检测到了死亡。

## 根因证据

三个初始 snapshot 都报告 `map.width=200, map.height=200`，但己方单位起点已经明显超出这个范围。游戏日志两次加载 `[p2]Small_Island (2p).tmx` 都记录 `Map size: 110, 110`。

原版 1.15 的地图类 `com.corrodinggames.rts.game.b.b` 字节码：

- 构造器设 n=o=20，p=n/2，q=o/2。所以 p/q 是半格偏移。
- 边界函数 c(int,int) 用 C/D 比较格坐标。
- 原生 i() 返回 C*n；j() 返回 D*o。
- alpha1 错误使用 p*n、q*o，得到 10*20=200。

客户端将目标夹入 [20,180]，使三个远处起点都向 (180,180) 行军。等到去程完成后，精确移动接口又按错误的 200×200 范围拒绝真实起点，返程完全没有入队。

## 修复内容

1. 状态输出、精确命令边界、旧版单次移动入口统一使用原生 i()/j()。
2. 状态新增格数和每格尺寸，便于检查世界尺寸。
3. 往返下令前验证起点在地图内，目标在地图内且位移为 40–160 世界坐标单位。与报告地图矛盾时零下令结束。
4. plan 记录地图宽高、计划距离和目标选择方式。可选指定附近目标，默认仍只做几何短移，不宣称寻路或水陆检查。
5. 版本提升为 0.01-alpha2，客户端要求同版游戏桥接层，避免替换文件但未重启游戏。

基于正确 2200×2200 尺寸，三组起点的默认目标分别是 (1110,1670)、(1108.95,1802.397)、(1060,1720)，直线距离均约 134.16；返程坐标均在地图内。

## 为什么前版测试漏掉

前版测试手工把 p/q 设成“地图格数”，复制了同一错误假设；模拟 HTTP 服务也使用了自洽的 1000×1000 场景，且未检查返回坐标范围。因此“测试通过”没有验证真实地图字段语义。

本轮回归使用原版地图构造器，保留 p=q=10，仅设置真实格数字段 C/D。先对旧 alpha1 JAR 运行，实际在 2200×2200 尺寸断言处失败（regression-before-fix.txt），再对修复版运行。接口测试还用三份报告里的原始起点作为返程目标，并校验矩形地图的宽高独立。客户端测试验证这三组坐标的短移往返，以及旧 200×200 错误输入下零下令。

这是原版对象/模拟接口验证，不是 Windows 实机寻路结果。需要用户在无敌军干扰的一局复测一次往返。
