# 给 GPT-5.6 Sol 的具体接续任务

## 合作方式

以本包0.04-alpha1为唯一起点。每轮做一个有界任务，交付文件和实际验证结果。预算少时减少重复读取/全量测试，不省略关键验证。不要启动子智能体、切模型、调用付费API或自动安装外部依赖，除非用户另有明确要求。不要重新设计整个项目，不把未完成的对战能力写成已有成果。

## 任务一：离线日志汇总器（优先；无需原版依赖）

交付：Python标准库脚本 analyze_reports.py、中文使用说明、三份随包报告的CSV/Markdown输出。输入一个目录，可递归读取opening/economy/development/roundtrip JSONL；不修改源报告、不连接游戏、不下令。

至少输出：文件名、版本、任务种类、最终outcome/phase/reason、现实耗时、commands、observations、实际新矿/工厂/坦克数、expansionStatus；保留原始summary字段。对development通过事件核对summary计数；识别缺summary、截断JSONL、坏行、重复完成ID、计数不一致，标成可区分的异常，不能把它们算成PASS。游戏事件间隔不得冒充游戏内时间。开矿出兵重叠用extractor_started/completed区间和tank_completed时间判断，说明这只是观察证据。

必须用本包三报告复核：0/0拒绝、0矿8兵PASS、1矿8兵PASS；第三份建矿期间完成2辆坦克。再加一个缺summary和一个坏行的小输入验证。优先做这个，因为几天后积累更多报告时可以自行汇总，不必每次由高额度模型通读全部快照。

## 任务二：矿点排除原因诊断（先解释，再改代码）

主要文件：developer/src/io/rwagent/bootstrap/EconomyBridge.java的openingPlan与site；客户端DevelopmentClient.nextMine依赖现有no legal opening site消息前缀，需兼容。

问题：visibleResourceCandidates只统计方框内当前可见资源格，用户无法知道为什么没有下一座可建矿。新增聚合诊断：搜索范围内可见候选、超过600圆形范围、完整占地不可见、原生合法性拒绝、最终合法候选。若引擎无法稳定区分占用/地形等，保留原生拒绝摘要，不凭猜测命名原因。

保持可见性检查先于读取地形/资源，不能披露未知矿点、敌人或雾中地形。规划必须零下令、零扣款、预览不登记世界单位。保持extractorT1/c_tank替换解析及实际模板。接口可追加字段，不破坏现有错误前缀、状态码或命令守卫。

验收：清楚区分“看到了资源格”与“可合法建造”；新增相关原版对象夹具，验证统计不改变既有选址与指令。再交可运行包及一次针对性复测步骤。没有游戏依赖时交具体补丁和未执行清单，不伪称已编译。

## 任务三：改善启动体验（前两项完成后）

先做只读预检：提示有无可用工厂、工厂是否忙碌、是否有建造者；缺厂明确推荐Economy或Opening，避免用户盲点Develop。在设计可靠的一键流程前，不要简单把多个BAT异步启动。

若进一步实现统一入口，需要同一个控制所有权、按完成结果推进；无工厂时建厂流程与已有忙碌工厂等待必须区分；不能因工厂忙而反复建厂。基础开局依赖可见空矿，不能把“找不到矿”误当整个建厂入口永远不可用。升级版本、说明回退并做关键故障测试。

## 后续核心方向：有限侦察与路径可达性

当前不能独立扩大视野，这是下一阶段能力缺口。先查清原生合法可达性接口，再设计有限目标、距离/时间上限、卡住退出的侦察小任务；不要直接让建造者向未知敌基地走，也不要读取雾中敌人或地图矿点作为决策输入。此项涉及新引擎映射，不建议在剩余额度极少时仓促混入上述维护工作。
