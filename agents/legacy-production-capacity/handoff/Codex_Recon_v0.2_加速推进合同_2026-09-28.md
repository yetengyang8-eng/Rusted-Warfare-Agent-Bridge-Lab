# Codex：Recon v0.2 加速推进合同（2026-09-28）

当前状态：World Model v0 已能保存合法敌情；Recon v0 已跑出“失联建筑 → 单兵核查 → 实际移动 → 合法重新目击”的原生行为闭环。用户希望继续加速，不需要每一小步都停下来让 DeepSeek 单独验收。

这轮不要把你锁死在“最小实现”。请你先判断现有架构、风险和时间，再决定一次推进到什么深度；优先形成用户能明显观察到的能力跃迁，而不是只增加日志/夹具。

## 推荐主方向
把 Recon 从“只会复查旧建筑”推进成真正的侦察子系统，优先考虑：
- Map Memory：区分当前可见、曾经见过、长时间未见、从未见过；让“浅雾/深雾/陈旧区域”可以被任务系统使用。
- EXPENDABLE_SCOUT：主力中战斗价值已经很低的残血单位可被“开除队籍”，转为侦察用途，不再参与主力 attack-move。
- FRONTIER_SWEEP：优先探索深雾、陈旧区域和高信息增益方向，不要浪费残血兵去扫主力附近刚黑掉的浅雾。
- 与现有 RECHECK_INTEL 共用 Recon Controller / 任务占有 / 主力排除 / 紧急召回框架，避免再做一套平行系统。

用户希望看到的核心行为是：主力继续战斗，而部分残血小单位被转岗，主动去长期未侦察区域或深雾执行侦察。## 允许你自行决定是否继续推进
如果基础稳定且边际成本合适，可继续实现第一版：
- SUICIDE_PROBE：已被判定为消耗型且逃生希望很低时，从“保命”切到“死亡前最大化信息增益”。
- 简单 Threat Field：区分敌方视野、攻击范围、速度/追击威胁；慢敌尽量绕边缘，逃不掉时才允许冲入危险区。
- Scout Capacity / Replacement：正规侦察者或侦察能力不足时，在经济允许条件下产生补侦察者需求。

这些不是本轮硬性交付项。你可以根据实际代码结构选择只做 MapMemory+FRONTIER_SWEEP，也可以一口气推进更多；但不要为了功能数量牺牲合法视野边界、主力稳定性和可回退性。

## 施工原则
- 隐藏敌人仍不得读现时位置/HP/生死/命令等真值；只允许消费合法历史与己方地图视野。
- 残血转侦察不应机械只看 HP；至少避免把仍有高战斗价值的关键重单位随便送掉。v0 可用可解释启发式，不必上复杂数学。
- 正规侦察与消耗侦察可以共用任务系统，但风险容忍度应不同。
- EMERGENCY/基地受压时不得让 Recon 抢走关键主力；必要时释放/召回。
- 新行为必须有开关或清晰回退路径；不要破坏现有 RECHECK_INTEL。
- replay checksum、多人/self-play、经济 vNext 本轮都不是主任务；除非有很低成本、高确定性突破，否则不要让它们抢主线。## 验收与加速方式
- 优先跑出至少一个自然原生局里的可观察片段：残血单位离开主力 → 接受 FRONTIER_SWEEP/其他侦察任务 → 实际移动到深雾/陈旧区 → 地图记忆更新。
- 如果自然样本不触发，可先用确定性夹具证明逻辑，再继续尝试原生局；不要为了等一个偶发事件无限耗时。
- 完整回归、候选 JAR 身份、安装件一致性仍必须保留。
- 可以使用你认为有帮助的子智能体。用户明确希望加速，因此不限制为最少数量；但仍建议保持“一个产品代码 owner，其他尽量只读/测试/审计/文档”，避免并发修改互相踩踏。
- 不需要为每个小步骤等待 DeepSeek 裁决。你可以连续推进多个安全 GREEN 循环，直到形成一个完整能力阶段、遇到明显架构分叉/高风险引擎操作/连续失败，再停下来交接。
