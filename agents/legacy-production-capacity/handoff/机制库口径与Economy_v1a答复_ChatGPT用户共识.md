# ChatGPT + 用户 → DeepSeek：机制库口径与 Economy v1a 共识

这是对 `问题清单_机制库情景口径_对话37.md` 的直接答复。重点不是继续核验数字，而是把**情景口径**和 v1a 的结构收束清楚。

## 1. 时间口径

- 用户确认：T1 矿由一个普通建造者从开始施工到完成，1x 下实测约 **16.7 普通游戏秒**。
- 项目早期反编译记忆：正常模拟约 60 tick = 1 普通游戏秒；经济归一化周期常见 40 tick ≈ 0.66 普通秒。因此“1 铁锈秒 = 0.66 秒”更像**经济周期口径**，不是所有 game-time 的通用秒。
- 因此当前工程继续按 `gameTimeMs / 1000 = 普通游戏秒` 使用；**不要把 16.7s / 58s 再乘 0.66**。
- 5x 只压缩 wall time；16.7 游戏秒在 5x 下仍是同样的游戏内时长，只是现实等待约变成 1/5。
- 若你要把“60/40 tick”写进正式文档或代码注释，建议快速定位早期反编译证据后再冻结；这不应阻塞主线。

## 2. T1 矿与回本

- 用户确认：**58 秒回本从矿建成后开始算**。
- 含义是单纯财务回本：矿自己把 700 成本赚回来后开始净赚；**与坦克机会成本无关**。
- 所以粗略可理解为 T1 矿收入约 `700 / 58 ≈ 12.1 资金 / 普通游戏秒`，用于先验估计可以；以后可由实机账本校准。
- 若从“现在决定投资”开始算完整回收周期，则至少是：builder 路程 + 16.7s 施工 + 58s 产出；不要把 58s 当完整投资周期。

## 3. 资源点 / 升级口径

- 普通资源点**永不枯竭**，矿收入长期恒定；不需要建“剩余储量”变量。
- T1→T2 升级期间，矿**继续按 T1 收入**产出；升级完成后才切换为 T2 收入。
- 所以未来比较“开新矿 vs 升矿”时，升级不是完全停产项目；应比较新增收入、升级成本、升级耗时与新矿的 builder 旅行/施工成本。
## 4. “满续兵经济表”口径

- ChatGPT 对表的读法，用户确认**正确**：`1.0 / 2.0 / 3.3 ...` 是生产时间倍率，不是“每 8.3 秒产出多少个单位”。
- 即更接近：小坦生产周期 = `1.0 × 8.3`，重坦 = `2.0 × 8.3`，猛犸 = `3.3 × 8.3`（具体单位仍沿机制库原口径）。
- “满续兵经济”表示维持该单位持续满产所需的经济能力；以后 v1b 可用来估算工厂消费能力。
- 但“几矿养一厂”不要硬编码成固定比例：还要计入基地收入、矿等级、兵种不同消费率和生产是否满载。

## 5. 机会成本：当前阶段不要把 58s 和坦克绑在一起

用户的理解：58s 只是矿自身财务回本。真正的“坦克机会成本”属于**战略层**，要看这 700 若变成即时军力，能否改变战场结果。

- 对称自对弈时，如果我比对手多两台坦克，而这两台已经足以改变局部战果/地图控制，则继续出兵可能更值；如果继续多两台也不能带来额外战略收益，就更适合把优势转成矿。
- 当前对手是“非常困难 AI”，其经济增速约为我们的两倍，**不能用对称玩家的相对兵力机会成本模型**。不要写成“领先 X 台坦克就开矿”。
- 等以后 Agent-vs-Agent、双方同经济规则，并且我们能估计战场情况时，机会成本才适合正式进入投资排序。

## 6. 用户给出的两个极端情景（用于检验未来结构，不要求 v1a 现在解决）

1. 超大图 / 几百密集矿 / 初始 5 万 / 出生很远：人类会持续造 builder → builder 造厂 → 厂继续产 builder → 大量抢矿 → 某区域矿开满后当地补厂并海量出兵。此时瓶颈不是钱，而是 **construction throughput**。
2. 小岛 / 1x / 4000 / 顶尖玩家：前期侦察坦克数量、塔区、矿区和战损都很敏感；是否牺牲即时优势开矿，要结合战损与对手行为判断。

这两个案例说明未来系统至少有三种产能：**矿 = 收入产能；工厂 = 军力转化产能；builder = 基础设施部署产能**。以后 `NEW_BUILDER` 应成为 Investment Candidate，但不是 v1a 范围。
## 7. 对 Economy v1a 的建议：先建立“经济主动抢预算”的能力，不要先解决完整战场判断

建议把“军队健康”换成更准确的概念：`MILITARY_URGENCY`（当前军事资金需求紧迫度）。不要马上把它写成固定 `army >= N`。

v1a 最小闭包可按：

- 基础经济已建立；
- 存在合法、安全的新矿机会；
- 当前不是明显 `EMERGENCY / 高压接敌 / 连续战损`；
- 当前军队不是明显贫弱；
- 则允许创建一次 `investment_intent(target=NEW_MINE,cost=700,chosenAt)`，把 700 变成 `investment_reserve`，普通生产不得花掉；
- 若期间出现明显军事压力，或 intent 在限定**游戏时间**内无法执行，则撤销 intent、释放 reserve、恢复生产；
- 不要求 v1a 正确预测“对手到底打不打得动我”，只要求能基于合法信息识别“当前有没有明显迫切的军事资金需求”。

建议的第一版状态可以很粗：`EMERGENCY / CONTESTED / STABLE / OPEN_EXPANSION`。输入只用合法可观测信号：近期 own losses、己方资产是否受击、敌军距经济区/主力是否很近、主力是否正在有效接战、军队是否明显低于常规作战规模。

**v1a 的真正验收，不要写死“第 4 矿必须 300–400s 出现”。** 成功链应是：
`investment_intent(NEW_MINE)` → `intentional_banking` → 至少一次普通生产因 `reservedFor=INVESTMENT` 被延期 → **army < mobileUnitHardCap 时新矿完成** → reserve 释放 → 生产恢复。

只要这条链成立，就证明 Agent 已经从“生产永远第一、剩钱才投资”进入“经济可以在合适时机主动拿预算”。具体是 300s、450s 还是别的时刻，交给局势决定。

## 8. 工程计量

支持补“完整支出账本”，这是 v1a/v1b 很值的基础设施。最小每笔记录：`gameTimeMs / category / cost / itemType / producerOrBuilderId / accepted`。
category 至少：`UNIT_PRODUCTION / BUILDER_RECOVERY / NEW_MINE / NEW_FACTORY / FACTORY_UPGRADE / MINE_UPGRADE`。
窗口收入估计可用：`Δcredits + 已知总支出`，再除以 **game-time delta**；这样以后可用自家实机数据校准 T1≈12/s 等机制库先验，也天然兼容 1x→5x。

请你基于当前代码与风险自行裁决 v1a 的最小实现；不要为了把 MILITARY_URGENCY 一次做成高手级战场评估而扩大范围。
